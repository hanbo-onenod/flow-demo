## Goal

When users double-click the exported order report CSV in Excel (Windows or Mac), Chinese customer names show as garbled text, so finance and customers have to re-save the file as UTF-8 with BOM before they can use it. Six reports (issues #14 to #18 and the 2026-11-10 product meeting) ask for this to be fixed. Make the exported file open correctly in Excel directly, by 2026-11-14 (Friday).

## Scope

- In: the encoding of the order report CSV export (`app/export_report.py`): write a UTF-8 BOM (`EF BB BF`) at the start of the file. T-001 kept the encoding unchanged on purpose; this task changes only that.
- Out: everything after the BOM stays byte-identical to today's output (columns, header, row order, values, formatting, CRLF line endings); no change to export speed (the T-001 result must still hold); no Excel (.xlsx) export; no other reports; no change to the finance import script or WPS setup.

## Acceptance criteria

- The exported CSV starts with the UTF-8 BOM `EF BB BF`, and the bytes after the BOM are identical to the current (pre-change) output for the same seeded data (`db.seed(conn, customers=20000, orders=10000)`, default seed). Checked by an automated test added to `tests/test_export.py`, run with `pytest tests/test_export.py`.
- Reading the new file with Python `encoding="utf-8-sig"` (as the finance import script does) gives exactly the same text as reading today's file with `encoding="utf-8"`. Checked in the same test run (`pytest tests/test_export.py`).
- All existing tests pass (`pytest`), and exporting 10,000 orders still takes under 1 second (`python scripts/bench_export.py`).
- Requester's definition of done: Chinese customer names display correctly when the file is double-clicked in Excel on Windows and on Mac; the requester accepts the automated BOM + byte-identical check above as the measurement. WPS and the finance import script must keep working as today (both read UTF-8 with BOM).
